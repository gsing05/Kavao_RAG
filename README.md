# Kavao Research RAG

Citation-grounded question answering over a curated, vetted research corpus.
Built so every answer traces back to a real source -- not a general model guess.

## How it fits together

```
papers/*.pdf -> extract.py -> chunk.py (parent+child) -> embed_store.py -> Chroma (children) + parents_store.json
                                                                                    |
                                              user question -> retrieve.py (search children, return parents)
                                                                                    |
                                                                          generate.py (Gemini, grounded in parents)
                                                                                    |
                                                                              answer + sources
```

`pipeline.py` ties retrieval + generation into one function (`ask_kavao`).
`main.py` is the FastAPI backend wrapping that in a web API + simple search page.

### Why parent-child chunking

Small "child" chunks (paragraph-sized) are what gets embedded and searched --
this keeps retrieval precise. But once a child matches, Gemini is given its
full "parent" chunk (the surrounding section) instead of an isolated fragment,
so it has real context to answer from. This takes advantage of Gemini's large
context window instead of wasting it on tiny disconnected pieces.

## Setup

1. Create a virtual environment and install dependencies:
   ```
   python -m venv venv
   source venv/bin/activate        # on Windows: venv\Scripts\activate
   pip install -r requirements.txt
   ```

2. Copy `.env.example` to `.env` and add your real Gemini API key:
   ```
   cp .env.example .env
   ```

3. Drop your PDFs into the `papers/` folder.

## Running it, step by step

Test each piece individually before running the whole thing -- Jupyter
notebooks are genuinely useful here, since you can inspect output at
each stage.

```
# 1. Check text extraction on one paper
python src/extract.py papers/somefile.pdf

# 2. Check parent-child chunking on one paper
python src/chunk.py papers/somefile.pdf

# 3. Embed children and store ALL papers in papers/ into the vector DB
python src/embed_store.py

# 4. Test retrieval alone (no LLM call yet -- see what PARENT chunks come back)
python src/retrieve.py "does cover cropping affect soil nitrogen?"

# 5. Test the full pipeline (retrieval + Gemini answer)
python src/pipeline.py "does cover cropping affect soil nitrogen?"
```

## Running the API locally

```
uvicorn main:app --reload
```

Then open:
- http://localhost:8000 -- simple search page
- http://localhost:8000/docs -- interactive API documentation (auto-generated by FastAPI)

## Building your evaluation set

`eval/eval_set.json` is where your verified (question, answer) pairs go.
Workflow: draft a candidate answer with Claude from a specific paper's
actual text, verify it yourself against the source, then save it as
`verified_answer` here. Once you have 15-20 pairs, run:

```
python eval/run_eval.py
```

This prints your verified answer next to what Gemini's RAG pipeline
actually produced, side by side, so you can judge where they diverge
and why (bad retrieval? wrong parent returned? Gemini ignoring the
retrieved text?).

## Re-running after adding new papers

Drop new PDFs into `papers/` and re-run `python src/embed_store.py`.
It appends new children and parents without needing to rebuild
everything from scratch.

## Deployment (later, once this works locally)

`main.py` is the entry point -- Render, Railway, and Hugging Face Spaces
all know how to run a FastAPI app via uvicorn. The `chroma_db/` folder
and `parents_store.json` (both created automatically when you run
`embed_store.py`) need to be included in the deployed version so the
hosted app has your actual data, not just your code.

A dedicated cloud vector database (Qdrant, Pinecone) is a reasonable
future upgrade once you outgrow a local Chroma DB -- `retrieve.py`
and `embed_store.py` are the only two files that would need to change,
since retrieval is kept behind a clean interface on purpose.

## Notes

- `EMBEDDING_MODEL_NAME` in `src/embed_store.py` and `MODEL_NAME` in
  `src/generate.py` are the two easiest knobs to swap later.
- Parent/child sizes are set in `src/chunk.py` (`MAX_PARENT_SIZE`,
  `MAX_CHILD_SIZE`, `CHILD_OVERLAP`) if you want to tune them once
  you've seen real retrieval results.
